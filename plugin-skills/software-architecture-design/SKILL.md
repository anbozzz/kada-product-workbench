# 软件架构设计

当前 Codex 任务负责技术判断和取舍，不创建常驻架构师 Agent。只把会改变方案且尚不明确的产品、临床、安全、成本或不可逆边界交给用户回答。

## 是否需要

出现以下任一实际影响时使用；先检查已有约束，仍足够时直接复用：

- 新建产品、服务、模块或共享能力；持续 HTML 产品需要决定页面、路由、组件、共享数据或源码构建边界。
- 改变模块/系统职责、依赖、事实所有权，或增删、合并、改写核心用户流程而影响这些边界。
- 改变核心对象、状态所有权、Schema、持久化、接口、事件、权限、安全、审计、临床风险或不可逆写回。
- 真实上线改变部署、容量、可用性、恢复、观测或迁移要求；现有事实仍不足以直接确定实现方案。

规模、文件数、技术名词或“以后可能上线”不单独触发。普通样式、文案、固定布局、局部修复及不涉及上述边界的一次性草图直接返回原任务，不生成架构文件或空目录。

## 输入、设计与写入

读取本批 PRD、正式工程入口、源码、接口和运行环境。PRD 足以支撑系统划分时即开始，不必等待所有细节定稿；本批需要的架构决定明确后才派生供实施的 Spec。已有架构足够时复用，不为每次功能修订重做。

通常使用 [架构设计标准](references/architecture-design-standard.md)：按产品要求选择工程机制，以系统、模块、数据和共同机制组织一份当前架构，保留清楚的标题、层级和编号。已有正式入口优先；无入口时使用 `architecture/designs/product.md`。不按页面操作节点拆分技术设计，不在 Spec 另存一套决定。

- PRD 负责产品行为；技术方案改变可用动作、保存结果、权限或其他产品结果时，先反馈并修订 PRD，保留实际确认状态。
- 架构负责共同技术方案及必要实施机制。不能把尚未设计的技术细节交给派生器临时推理。
- Spec 通过产品文档 Skill 的 [派生合同](../product-documentation/references/spec-derivation.md) 引用技术来源；修改 Spec 的技术意见回到相应架构章节处理，检查相关功能影响后重新派生。
- 已有 Spec 中的有效技术设计只有在明确迁移范围内才迁出，保留稳定决定 ID、状态及引用；历史和人工 Map 不自动迁移。

需要成品对照时读 [完整示例](references/example-cross-module-architecture-design.md)。只有 Project 已采用多文档管理、独立 ADR 或确需多方 RFC 时，才读 [独立决定与路径](references/artifact-lifecycle.md)；不默认创建成套文件。维护 Skill 方法依据时才读 [方法来源](references/source-basis.md)。仅查看、映射或程序转换不触发新设计。

## 完成

技术决定说明原因、范围、明确不改、否决方案和回归检查；不改写产品规则。候选、已采纳方案与已实现事实分开。运行对应文档检查及 Project 验证，报告实际证据和未知；脚本通过不证明方案正确。实现与验证应能依据结果继续，不建立平行事实源。
