# 架构设计内容与验证

## 1. 从 PRD 到技术设计

读取完整功能及适用公共规则，辨认哪些产品行为需要工程保证；结合当前源码、接口、运行环境和已有架构，复用足够的机制，仅补本批缺口。缺少产品决定回 PRD，缺少技术机制由当前任务设计；缺少外部事实时标明候选合同、仿真或待接入边界，未知不能当成不适用。

普通产品任务在一份独立架构设计维护技术决定，Spec 为其派生视图。架构说明谁负责、怎样实现、为何这样选择以及如何验证，不重述 PRD 的点击规则，也不要求产品用户选择算法。业务模块不预设为服务；没有后端的持续 HTML 产品仍需处理适用的组件、状态和构建边界。

## 2. 工程覆盖与表达

按实际影响选择下表内容，不逐格填空。每项设计引用所支撑的需求 ID，用具体对象、输入输出、顺序、成功依据和恢复机制回答问题；不以“保证一致性、支持重试”代替方案。产品可见行为沿 PRD，不在下表再定义一套。

| 设计面 | 何时适用 | 必须明确的工程内容 |
|---|---|---|
| 实现基线与边界 | 形成实施说明 | 唯一源码及 Git（若有）、版本、运行构建入口、依赖环境、沿用及新增范围；区分已有、待建、仿真，未有工程时标拟定。 |
| 模块职责与依赖 | 新建或改变模块、共享能力或跨模块调用 | 提供者与消费者、公开边界、依赖方向、业务事实修改权；实际输入输出、交接责任和调用顺序。 |
| 页面、路由与组件 | 建设持续修改的界面 | 页面身份到路由及实现入口的对应，多入口复用、参数、直接打开、返回及上下文恢复机制；公共组件输入输出及差异。 |
| 数据模型与持久化 | 读取、修改、关联或保存数据 | 稳定身份、逻辑模型、关系与约束、权威读写入口、保存介质及提交点；历史、删除、缓存失效和适用迁移。 |
| 状态与事件 | 业务生命周期、共享状态或异步事件 | 业务、跨页面及临时编辑状态的所有者，合法迁移、事件顺序和联动机制；防止陈旧结果覆盖。 |
| 接口与外部依赖 | 服务、设备、外部系统或异步任务 | 请求响应、身份及关联键、错误分类、时限、取消语义、版本兼容与责任；已有合同引用固定版本，待建合同定义到可实施程度。 |
| 事务、并发与幂等 | 多步写入、重复触发或竞争修改 | 原子范围、冲突检测及裁决机制、同次操作身份、去重期限、版本检查或锁的必要性、乱序结果处理。 |
| 失败、核实与恢复 | 依赖失败、部分完成、结果未知或中断 | 区分未执行、失败、成功与待核实，关联并查询原操作；重试范围与次数或截止条件、补偿、断点及人工接续，避免重复产生事实。 |
| 权限、安全与审计 | 鉴权、敏感数据、审计或不可逆写入 | 可信校验边界、访问及数据范围、会话失效、脱敏、密钥、留痕和更正机制；演示开关不证明真实权限。 |
| 质量、容量与可观测性 | 时效、规模、可用性或排障要求 | 在约定环境下满足响应、资源与可用性的机制，达标及排障指标、关联信息和降级机制；未知数值标候选或待确认。 |
| 仿真数据与接入边界 | 演示数据或替代真实服务 | fixture 身份、初始场景、重置、内存或本地保存语义、真实接入替换位置；不把候选规则硬编码成生产事实。 |
| 构建、交付与运行 | 交付可运行制品 | 一套源码生成唯一当前产物，单文件或目录、双击或启动方式、资源与网络依赖、离线能力；路由匹配打开方式，修改回源码。 |
| 部署、迁移与回滚 | 真实运行环境或数据升级 | 部署单元、配置、版本兼容、迁移顺序、备份恢复、回滚和运行责任；影响可用时段或数据保留时先反馈 PRD。 |
| 验证与回归 | 每批必要设计 | Project 统一验证入口、代表性数据、成功与关键失败场景、证据方法；验证产品结果和工程机制，不把文档检查当作实现。 |

图表达决定，不各自形成新流程或文档。按问题选择：职责或概念不清用领域边界；静态依赖用必要层级的 C4；调用顺序、失败和并发用时序图；合法迁移用状态图；身份、基数、唯一性和一致性用 ERD；运行节点、网络或灾备影响方案时用部署图。简单布尔状态不单独画图，C4 不默认画全层级，领域分析不要求微服务。

图标题说明问题和视角；节点有名称、类型及责任，关系有方向和含义。图后说明关键边界、失败与未知；状态图含初始、终止和阻断条件，时序图含关键失败路径，部署图区分运行节点与软件单元。

重要质量要求写清来源、触发、环境、受影响对象、响应及可验证指标，并用 ID 关联验证；指标未知写 TBD，不用“高性能、稳定、安全”代替判定条件。已有 PRD 质量目标引用其来源，架构补实现和验证机制。

## 3. 成文、标题与状态

普通任务按实际需要使用下述设计内容，不强制八章模板、空栏或独立 ADR。新文档可按下列编号标题组织适用内容，省略不适用章节后连续编号；既有文档保留原有标题、层级和编号，只修改受影响范围。连续操作顺序编号，并列规则分项，失败分支用明确的小标题，图表紧邻解释。

1. **结论与适用性**：为什么需要设计、当前状态、主方案。
2. **目标、范围与依据**：产品与技术来源、范围内、明确不改、未知及影响。
3. **架构驱动因素**：真正改变选择的不变量、硬约束和质量要求。
4. **整体设计**：按第 2 节适用内容写清系统、模块、数据及共同机制，不按页面操作拆分。
5. **候选方案与取舍**：主方案和真实可行的更简单候选、收益及代价；没有第二个可行方案时说明原因，不凑选项。
6. **实施、迁移与回滚**：适用的实施顺序、兼容、迁移和回滚点。
7. **验证与可观测性**：各驱动因素对应的测试、检查、指标、日志、告警或人工 Review。
8. **决定、风险与后续**：稳定决定 ID、理由、否决方案、影响、回归检查、残余风险及重访条件；独立 ADR/RFC 仅在已采用时链接。

沿用八章格式时使用 [设计模板](../assets/architecture-design-template.md)，不得省略或改名其固定章节，不适用项简述原因。需要成品对照时读 [跨模块示例](example-cross-module-architecture-design.md)。

技术状态固定为 `proposed → adopted → implemented → superseded`：分别表示候选或仍有关键未知、已完成技术取舍可指导实现、已实现且完成约定验证、已被替代并链接替代项。技术采纳不等于产品确认，不用 `confirmed` 表示 Agent 自己采纳，也不用 `implemented` 表示只写完文档。

## 4. 来源、派生与变更

独立架构维护接口合同、共同机制及必要的适用条件与执行顺序，并通过需求 ID 说明适用范围。具体代码、迁移脚本及测试归源码；已在那里维护的合同精确引用，架构仍须能说明关键技术边界。

供派生的完整技术章节在标题后紧跟稳定 `<!-- architecture-id: 实际语义ID -->`。改标题、编号或顺序保留 ID；拆分、合并或替代时核对关联。元数据、说明、风险和未决正文也须落在已标记章节内，不能只标“整体设计”而遗漏文档其余正文。以模块或共同机制确定引用范围，不按 Spec 节点复制设计。

来源提取、context、范围外声明及手改回执统一沿 [Spec 派生合同](../../product-documentation/references/spec-derivation.md)。该程序按标题边界取完整原文，不重写规则，不自动追读外链；当前一次只接收一份选定架构来源。既有多文档项目不能仅放 ADR 链接就声称决定正文已进入 Spec，也不能为派生擅自合并、迁移或另建重复决定源。

技术方案改变可用动作、保存时机、可见范围、冲突裁决、允许丢失的数据或失败后的继续方式时，先说明原行为、技术约束、建议行为与影响；将本次产品决定写回 PRD 并保留实际确认状态，再更新架构并重新派生受影响 Spec。仍未决定时在对应来源保留一致的未知与临时边界，不阻断无关功能；尚未授权 Spec 时不提前生成。

Spec 手改的技术意见回对应完整架构章节及直接依赖修订；产品意见回 PRD。已有待同步改动时，经来源复核、候选预览和回执后再发布，不以更新架构直接覆盖手改。历史入口、确认版本和人工 Map 只在明确迁移范围内处理。

## 5. 完成检查

1. 对照 PRD 和实际证据，核对适用设计面、事实与候选、责任和未知；产品行为未被技术方案静默改写。
2. 沿关键运行路径检查职责、调用、状态数据、失败恢复、迁移与验证是否自洽；图文一致，实现人员不必重新猜测。技术不足回对应模块补齐，不交给派生器推理。
3. 核对标题、编号、稳定 ID、引用及实际状态；旧定义和直接引用随变更修订，替代决定保留关联。
4. 八章设计、ADR 或 RFC 从 Skill 目录运行 `python3 scripts/validate_architecture_artifact.py <文件路径>`；普通按需格式核对语义、ID 和引用。格式校验器保留对未采用派生的旧文档的兼容，不以它判断来源就绪；派生另由程序检查 ID、完整正文覆盖及关联。结构通过不证明设计正确。
5. 实际制品沿 [统一 Spec 验收](../../product-documentation/references/product-spec.md#36-验收与变更影响) 和 Project 验证；纯文档改动只检查语义、格式与引用。报告实际证据和未决项，不把设计采纳、实现验证和产品确认混为一项。
