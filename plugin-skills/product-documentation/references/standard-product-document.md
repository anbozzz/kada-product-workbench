# 面向研发的产品需求文档

交付一份连续可读的 `{产品名称}产品需求文档.md`，在页面建设前明确产品定义。PRD 定义产品行为，独立架构维护技术设计，Spec 按明确来源程序派生；只展开本批适用范围。

## 编写方法：先划分业务，再定义操作与场景

1. **明确范围。** 从目标和来源识别角色、业务对象、生命周期、用户任务、起止边界及上下游。新建提出可评审方案；修订保留有效决定，新增提议与已确认内容分开。
2. **划分模块。** 按共同业务职责归组任务，在“功能架构与模块职责”说明划分依据及负责、不负责的范围。职责、事实处理权或交接不同可拆分，页面、角色、入口或代码目录不同不单独构成理由。跨模块明确主责、承接方和交接内容。
3. **拆分功能。** 以主体、对象、起止边界和结果定义功能；可分别发起并取得独立结果的任务分开，同一任务的步骤、输入方式和条件变化保留为操作或场景。操作归属清楚、差异可具体表达即停止，不按按钮数量或固定深度拆分。一页可承载多个功能，一项功能可跨页面。
4. **推导场景。** 先明确操作前提、顺序、生效结果和后续去向，再沿读取、判断、写入和交接步骤，按下表识别条件变化。前提改变或结果无法确认时，写清是否继续、已有结果和输入的处理、允许或禁止的动作及继续条件，再写反馈。正常分支与故障分开，只展开改变路径、结果或恢复方式的场景。
5. **接续必要架构。** PRD 足以支撑技术设计后、Spec 派生和实现前，按实际影响使用或复用 [架构设计](../../software-architecture-design/SKILL.md)；影响产品定义的可行性问题提前核实。业务模块不预设工程划分，独立架构说明如何承接产品职责。技术方案改变功能边界、事实归属或用户可见结果时，先修订 PRD，保留实际确认状态，再按来源派生 Spec。
6. **按完整操作成文。** 首次成稿就按读者理解功能的顺序，写清谁在什么情况下操作什么、得到什么结果及怎样继续；用下表回查全部适用内容，不把检查类别逐项抄成正文栏目。新增规则回到所属操作或共用规则中整理，不在其他栏目末尾追加孤立说明。先交代场景发生在哪一步、什么条件变化，再写处理与去向；正常流程已写清的行为不另段重复，不补与该操作无关的副作用否定。未知按第 2 节处理，不把未设计、未实现或原型未展示当成不适用。
7. **整体回查与表达整理。** 按第 5 节推演完整任务、修正原定义及直接引用，不追加平行解释；再沿 Skill 入口接续保真整理、独立复核与评审。检查不代替首次设计。

## 1. 文档结构与完整性检查

文档外层结构与稳定 ID 用于工作台识别，按第 3 节保留。功能内部按实际操作组织；下方单项功能表用于检查完整性，不规定正文栏目名称。

### 文档整体设计

按下列顺序组织一级文档内的二级章节。文档状态、适用版本和来源说明放在开头；适用章节中再按表内标准三级标题组织。除“详细功能说明”和“全局产品规则”使用后文专门层级外，不为一个章节重复建立同义栏目。

| 二级章节 | 标准三级标题 | 何时适用、必须回答什么 |
|---|---|---|
| 产品概述 | 产品目标与成功标准 | 必有：解决谁的什么问题，怎样的可观察业务结果表示目标达成？产品成功条件在此明确，供 Spec 按来源派生。 |
| 产品概述 | 版本范围与非范围 | 必有：本期覆盖什么、不覆盖什么，目标终端及交付模式是什么；候选、仿真、已有与待建设的边界是什么？ |
| 产品概述 | 用户角色与使用场景 | 必有：谁发起、参与和承接任务，在什么环境与条件下使用？没有登录体系也须说明目标使用者，不虚构角色权限。 |
| 核心业务概念 | 业务对象与术语 | 存在业务对象或需统一的术语时：含义、稳定身份、关系与生命周期是什么？ |
| 核心业务概念 | 事实来源与业务责任 | 读取或改变业务事实时：值从哪里取得，谁有权定义、修改和裁决；冲突以谁为准，哪些事实未知？不把取值位置当成权威来源。 |
| 产品整体结构 | 功能架构与模块职责 | 必有：能力如何分工，各模块负责什么，覆盖哪些目标？模块不强制等同页面或代码目录。 |
| 产品整体结构 | 信息架构与导航 | 有用户界面时：信息如何组织，主要入口、层级和复用关系是什么？页面身份按明确设计供 Spec 登记，技术路由细则归独立架构。 |
| 产品整体结构 | 核心业务流程 | 必有：从发起到结果生效及后续使用的主链是什么，如何交接与结束？简单任务可短写，跨角色或跨页面流程应有流程图。 |
| 产品整体结构 | 跨模块与外部协作 | 存在协作时：提供者、消费者、输入输出、业务责任和失败承接方是谁？全局明确责任，各功能写具体交接行为。 |
| 详细功能说明 | 业务功能域（使用实际名称） | 必有：按下文“单项功能设计”完成各功能，跨页面流程在功能域交代主链并连接主责功能，不复制另一套旅程。 |
| 全局产品规则 | 实际共用规则（使用业务规则名称） | 至少两处对象、条件、例外完全相同且须统一时：完整定义规则与适用范围；功能带入本次具体处理及局部差异。 |
| 全局产品规则 | 产品质量要求 | 存在跨功能质量要求时：按适用的响应时效、容量、易用性、可访问性、兼容性、离线、安全与隐私场景，写环境、触发、可观察响应和判定条件。局部要求归功能；没有依据的指标标候选或待确认。 |
| 待确认事项 | 不另设固定三级标题 | 存在未决问题时：简短索引到原位置，指出影响范围和所需决定或证据，不重复正文。 |
| 版本记录 | 不另设固定三级标题 | 必有：版本、变化与实际确认范围，不把生成授权当成产品确认。 |

### 单项功能设计

“详细功能说明”按“三级业务功能域 → 四级具体功能 → 五级操作或主题 → 必要时六级场景”组织，不随分析深度增加目录或交接制品。功能以任务命名；页面名仅在能准确表达任务与边界时使用。

目标、入口与前置条件、正常操作及结果必须写清，但不要求各占一个标题。简单功能可用短段说明，复杂功能以实际操作命名五级标题，必要时展开六级场景。同一操作的交互、条件、结果及局部分支集中在一处完整说明，其他位置只作必要的精确引用。跨操作规则统一定义，不能因就近放置而缩小适用范围；单项校验写在字段旁。多个操作仅在条件、结果和继续方式全部相同时合写。

连续步骤按顺序编号，条件步骤保留触发条件；可选操作、取消、异常和恢复按具体操作或场景设五级或六级标题，不接在正常步骤后编号成必经流程。并列规则分条，短内容不强加标题，不为所有功能规定相同细节顺序。

| 完整性检查类别 | 何时适用 | 必须回答什么 |
|---|---|---|
| 目标与范围 | 每项功能 | 谁通过本功能解决什么问题，处理什么对象，做到哪里，完成后的业务结果是什么？ |
| 入口与前置条件 | 每项功能 | 从何处或何种事件进入，携带哪个对象和上下文，须满足什么角色、业务状态或依赖条件？ |
| 正常流程与结果 | 每项功能 | 按顺序说明角色或系统的动作、反馈、数据与状态变化、结果何时生效及后续去向；纯展示写展示与结束方式。 |
| 展示与交互 | 有界面或可操作区域 | 显示哪些信息与主要操作，信息优先级、默认选择、联动及只读、禁用和操作反馈的条件是什么？涉及查询、筛选、排序、分页或选择时定义其范围及联动。布局提议配对应功能线框；技术路由和控件实现归独立架构或源码。 |
| 数据字段与校验 | 输入、读取、计算或输出业务数据 | 字段含义、来源、类型、单位、精度、时间口径、枚举、必填条件、默认值、可编辑性、关联与合法范围是什么？计算写公式或规则及缺值口径；区分空值、零值和未知。只写影响产品行为的数据语义，不复制物理接口字段。 |
| 业务规则与约束 | 存在资格、匹配、优先级、互斥或必须始终成立的业务条件 | 规则对哪些对象在何时生效，如何判断，优先关系和例外是什么，违反后怎样处理？跨流程不变量在此定义，具体分流与失败路径写入相关操作或场景。 |
| 条件分支 | 正常业务存在不同处理路径 | 哪个条件从哪一步分流，条件重叠或无匹配时如何选择，顺序、处理结果与合流点是什么？ |
| 状态与流转 | 对象或任务具有业务状态 | 状态含义、初始与终止状态、允许迁移、触发者、动作限制及对其他功能的影响是什么？界面加载状态归“加载与空态”。 |
| 角色与权限 | 可见、可操作或数据范围有差异 | 谁能对什么资源在什么条件下查看或操作；无权、权限失效或操作中角色变化时如何反馈、保留输入并继续？不把角色名称当成权限规则。 |
| 保存与生效 | 修改需保留或向他人可见 | 何时保存、保存范围、草稿与正式结果区别、成功依据、何时对谁生效、保存后如何回看或更正？历史保留与删除规则适用时写明。 |
| 取消、返回与再次进入 | 离开影响未保存内容、进行中操作、恢复位置，或不同退出方式有不同结果 | 从哪个页面、哪一步以何种方式离开，内容如何处理，是否需确认，去向及再次进入的结果是什么？普通关闭、返回在正常流程写清即可；意外中断另行说明。 |
| 跨模块与外部交接 | 消费或输出其他能力的事实 | 谁向谁交接哪个对象及上下文、时机、对方接受或拒绝的结果，谁有权修改状态，后续如何查阅和继续？故障按下方分类检查，按操作归属成文。 |
| 通知与待办 | 有跨用户消息、提醒或待办 | 触发条件、接收范围、内容、时机与去向是什么，业务完成、已读或撤回后如何更新，重复与发送失败如何处理？发送成功不等于对方已处理。 |
| 导入、导出、打印与批量处理 | 提供这些能力 | 对象范围、选择规则、内容与格式、顺序、脱敏、处理上限及结果交付方式是什么？导入的字段匹配、校验和重复数据如何处理？逐项结果、部分完成与失败恢复按对应分类展开。 |
| 安全、隐私与留痕 | 涉及敏感数据、追责或不可逆动作 | 可见与脱敏范围、确认或复核条件、记录什么及谁可查看、允许怎样更正或撤销、保留与删除的业务要求是什么？医院和监管口径无依据时不得补造。 |
| 质量与使用约束 | 存在本功能特有质量要求 | 在何种设备、网络、数据规模或辅助使用环境下，响应、可用性和兼容性须达到什么可观察条件？与全局相同的要求精确引用并交代本功能影响。 |
| 加载与空态 | 数据需加载或可能为空 | 等待时显示什么、能否操作，初始无数据、查询无结果与数据未取得如何区分，各自能做什么？ |
| 输入错误与校验反馈 | 输入、选择或提交可能不合法 | 在何时校验，定位哪项问题，提示什么，阻止哪些动作、保留哪些输入，怎样修正并继续？字段合法规则在“数据字段与校验”维护，此处落实失败路径。 |
| 对象与状态变化 | 进入后对象可能被修改、失效、删除或改变状态 | 何时发现变化，旧信息怎样标识，哪些动作停止，用户输入如何保留，怎样更新上下文或重新选择对象？ |
| 重复操作与并发冲突 | 动作可重复触发，或多人、多端可同时操作 | 怎样区分再次执行与同一次操作，重复时用户得到什么；冲突按何种业务优先关系处理，能否覆盖、合并或重做，对他人结果有何影响？技术去重和锁机制归架构。 |
| 依赖失败与超时 | 依赖网络、服务、设备或异步任务 | 在哪一步失败或超时，已知哪些事实，当前显示及操作限制是什么，谁可重试或转交，已有结果和输入怎样保留？超时无法确认是否生效时转入“结果未知”。 |
| 部分完成 | 多步或批量任务可能只有部分步骤或对象完成 | 怎样区分已完成、失败和未执行部分，哪些结果可继续使用，怎样展示逐项结果、仅重试受影响范围、撤销或人工接续？已成功步骤不得因整批重试而重复产生结果。 |
| 结果未知 | 发起操作后无法确认是否已经生效 | 怎样展示待核实状态并限制再次执行，以哪个原操作或对象查询确认，由谁在何时核实；确认成功、确认未执行或持续无法核实时分别如何继续？不能把未知当失败；这里是运行结果未知，不是设计尚未决定。 |
| 中断与恢复 | 刷新、关闭、会话失效、断网或进程中断会影响任务 | 中断时业务是否继续，重新进入如何识别进行中与已完成任务，恢复哪些输入和进度，何时失效、重做或人工接续？不能把恢复一律写为“重试”。 |
| 数量、时间与范围边界 | 数量、时点、有效期、精度、选择范围或次序影响结果 | 零、一、多及上下限，临界时点与过期、日期跨界、舍入及范围组合分别怎样处理？只展开改变业务结果的边界，给出具体规则；未知阈值保留待确认。 |

从“加载与空态”到“数量、时间与范围边界”仍逐类识别异常与边界，权限拒绝和正常取消也须在首次设计时考虑。仅影响单一操作的场景可就近完整说明；涉及多个操作的场景按决定其主要结果的类别统一定义。已完整定义的内容不为分类重复建栏目；需要跨处查阅时，精确引用具体操作或场景并说明本处影响。呈现位置变化不减少检查类别，也不能把失败、部分完成和结果未知合成一种处理。

### 层级与写法示例

以下以 MDT“转移群主”为完整功能写法示例，示范连续步骤、取消和不同失败路径怎样放在同一功能内。业务规则仅适用于该示例，不作为其他产品的默认要求；标题按功能需要设置，不照搬成通用模板。

```markdown
# 产品名称产品需求文档
<!-- prd-profile: 可映射PRD-v1 -->

> 文档状态：草稿
> 适用版本：v0.1

## 4. 详细功能说明

### 4.2 中心群

#### 4.2.3 转移群主
<!-- prd-section-id: 需求-中心群-转移群主 -->

当前群主可将管理权转交给本群另一位有效成员，自己继续留在群内，成为普通成员。

##### 选择并确认转移

1. 从群设置进入转移群主，单选本群内除本人外的一位有效成员。群外人员必须先入群；系统不自动替换接管人。
2. 选定接管人后，确认框显示双方姓名，以及“转移后你将成为普通成员，不能再管理本群”。
3. 群主确认后直接提交转移，不需要接管人审批。群服务确认成功后，各端更新管理权限：新群主获得管理权，原群主成为普通成员。群人数、群消息、患者和 MDT 均不变。

在选人页返回群设置，或在确认框点击“取消”，均保留当前群主。

##### 群主变更通知

转移成功后，全体成员收到群主变更通知。取消或转移失败时不生成通知，重复回执不重复显示通知。

通知缺失时，在再次加载时补充通知；不回滚群主身份，也不重新执行转移。

##### 无法完成转移时

| 遇到的情况 | 系统处理及后续操作 |
|---|---|
| 提交时，操作者已不是群主 | 告知操作者本次转移未执行；关闭管理操作并刷新角色，不继续提交原选择。 |
| 接管人账号失效，且服务确认本次转移未生效 | 提示“接管人账号已失效，请重新选择群主”；返回选人页，将该账号标为不可选。 |
| 接管人已离群 | 要求重新选择本群内的有效成员。 |
| 服务明确返回其他失败 | 提示“转移群主失败，请重试”，保留原群主和所选接管人。App 确认操作者仍为群主、接管人仍有效且在群内后，允许重试；用户也可取消并返回群设置。 |
| 网络中断或超时 | 提示重试。重新进入群设置时读取当前群主：已转移则按新身份显示权限，操作者仍为群主时可重新操作。 |

同一次转移不重复执行。
```

示例保留四级功能、紧随标题的稳定 ID 和五级操作标题；全文仍按适用整体章节组织。简单功能可用短段写清，不强加这些标题；复杂操作可用六级场景展开具体路径。功能内操作或场景不单独生成需求 ID；是否具有独立页面身份由产品与架构中已明确的页面职责和导航设计确定，Spec 按来源登记。

## 2. 表达与取舍

- 用准确的书面中文写动作、结果、约束和例外。场景推导与分类用于保证覆盖，成文按本功能的理解需要组织，不给所有功能套同一种细节顺序；保留全部适用内容和完整判断逻辑。
- 一个段落围绕同一操作或判断展开，条件、处理及例外就近保留。长段混有不同对象、操作或生效时点时，按含义分段、分条或使用操作、场景标题；连续步骤保留顺序，不能把共同前提拆成只约束某一条，也不能让新增小标题缩小原规则的适用范围。简单功能保持短写，不逐句加标题。
- 沿操作讲清从进入到结果及去向，把界面表现、提交条件、生效依据和相关例外放在对应操作附近，不让读者跨多个分类栏目拼接同一路径。详细字段、映射和跨操作规则保留完整定义，操作处按需精确引用；不另写一套简版规则，也不靠摘要代替约束。
- 公共规则在责任位置完整定义，各功能交代适用条件、处理及局部差异后精确引用。仅对象、条件、例外都相同时合并；保存、自动保存、历史保留等不同语义不能混同。
- 修订以当前有效需求及本轮明确变更为依据。在授权范围内允许整段重写、调整叙述顺序、拆合段落和改写功能内标题；保护业务含义，不要求保留原句形状，叙述顺序变化不得改变业务执行顺序。未变更部分保留角色、范围、数值、状态、权限、术语、条件、例外及“必须、可以、不得、待确认”等确定程度；不借润色新增解释、补齐未知规则或用抽象概括替代具体对象与动作。功能明确废弃或实质调整时，可按新逻辑删除或重写，并同步关联内容。
- 未知和冲突就地说明问题、当前处理与影响；范围外、未实现、原型未演示分别说明，不混同。
- 表格用于并列比较和稳定映射；独立步骤及恢复分支须展开，不能压成一句结论。截图紧随对应功能，不用近似截图穷举状态；删除不适用内容和模板提示。
- API、物理数据、缓存、事务、部署、代码结构和构建约束归独立架构，测试实现归源码。验收依据来自 PRD 的产品结果及架构的机制验证要求，供 Spec 引用；不在派生时补业务规则，不把技术细则、研究日志和追踪总账塞进 PRD。

## 3. 可映射 PRD 格式

首次生成或修订时即使用 `可映射PRD-v1`，不以已有 HTML、页面绑定请求或独立标准化任务为前提：

- 一级标题后有 `prd-profile`；文档状态、适用版本非空，版本按 Project 约定，未指定时从 `v0.1` 开始。
- 每个四级功能章节有唯一 `需求-...` ID；每个实际三级全局规则有唯一 `规则-...` ID，紧随标题。需求 ID 标识功能，页面或关键区域是映射目标，两者可多对多关联；映射不改变前述功能边界。
- 改标题、编号、顺序、正文或所属功能域时保留 ID；只有语义拆分、合并、废弃时才调整，并提示受影响的引用。隐藏 ID 不作为冗余删除，也不额外生成需求单元或追踪表。
- 功能章节必须有正文；五级标题按实际操作或主题命名，六级标题按需细分场景，不要求固定栏目名称。历史结构仍可读取，局部修改不为换格式重写无关功能。
- 调用工作台 `parsePrdMarkdown`，检查返回的 `valid` 和 `errors`：插件内位于插件根的 `src/prd-service.mjs`，Workspace 内位于 `apps/interactive-product-spec/src/prd-service.mjs`。不可调用时按本节自检，并说明未运行校验器。旧工具若仍要求固定四小节，报告工具不兼容并按本标准自检；工具升级需在授权范围内，不得为通过校验把设计压回旧模板。
- 本任务草稿的格式遗漏直接原位修复、复查；外部或历史非标准文档保留原件，在 `drafts-documents/` 建立或继续对应标准化草稿。生成 ID 和格式通过均不自动创建 `prd-map.json` 或确认产品内容。

## 4. 草稿与确认版本

新建和修订的普通 PRD 写入 `drafts-documents/`，同一草稿原位更新，不按评审轮次复制。只有用户明确确认整份当前文档时，才将其和打开所需资源一起移入 `confirmed-documents/`，文件名加不可覆盖的版本后缀；未指定版本时首次 `v0.1`，之后递增。已存在的 `prd-map.json` 必须与 PRD 一起冻结；原型只有被同时点名才一起确认。

确认后 Draft 不保留同一制品，后续修改从最新确认版重新派生草稿；保护历史确认版本并同步 Project 入口引用。局部认可、作者自检和渲染通过不触发整份确认。Spec 沿当前 Project 生命周期，历史文档只在明确迁移范围内处理。

## 5. 交付检查

分开检查并修正原章节：

1. **业务保真**：对照来源，范围、条件、例外和待确认项未被改变；对已有评审原型核对独立业务操作，尤其改变数据、状态、权限或他人可见结果的动作。纯展示和常规控件不必拆成独立功能；影响任务继续或数据保留的行为仍写入所属标题。
2. **逐功能复读与场景推演**：只读成稿及必要来源，不借前期解释，能否确定谁在何处、哪一步、什么条件下操作哪个对象，随后发生什么、怎样继续？需要猜测时，能从正文唯一还原的补明，存在不同合理行为的回到设计。删去一句若不改变行为理解且不丢失事实、边界或待确认项，则删除；重复定义合并。对照任务主链检查遗漏、职责重叠、交接与冲突，不以标题齐全判定完整。发现一类问题，检查本次范围内同类场景；用户指出全文问题时复检全文，修改后重读受影响完整功能。
3. **阅读定位与归位核对**：选取实际任务，检查能否连续读懂操作、关键限制及失败后的继续方式，不以字数或段落长短证明更易读。移动或合并说明时，逐条对照原文核对去向、对象、条件、时点、结果和例外，检查标题与编号未改变作用范围、引用仍准确；不能只凭关键词仍在或 Agent 能推回原意判定保真。
4. **格式与交付**：格式校验、ID 保留、截图链接、版本和确认范围正确；没有将技术或测试设计混入正文。

交付当前文档、实际检查与仍需决定的问题；结构检查和作者自检不等于独立评审、技术验收或用户确认。
