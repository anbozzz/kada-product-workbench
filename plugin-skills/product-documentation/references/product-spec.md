# Product Spec 标准

Spec 保留为可追溯的研发视图和用户反馈入口。产品行为由 PRD 维护，技术设计由独立架构维护；正常生成由程序按明确关联取出原文，不由 Agent 重述产品规则、补造机制或重新拆分页面节点。

## 首次采用与来源更新

读取本批 PRD、Project 工程入口及已有架构。PRD 已足以支撑技术设计后，使用 [架构 Skill](../../software-architecture-design/SKILL.md) 明确或复用本批系统、模块、数据与协作决定；产品缺口回 PRD，技术缺口回架构。来源尚不完整时明确范围与未知，派生器不补齐设计。

按 [派生与手改同步合同](spec-derivation.md) 维护一次明确来源绑定，运行程序生成或刷新 Markdown Spec。稳定需求、架构和操作 ID 保留；来源状态、范围及引用变化按源文档方法核对。正文由完整来源引用块呈现，技术设计不伪装成业务节点。自动检查引用、范围声明、原文、结构和版本，不反复执行 Spec 全文内容审核；来源设计及实质修订才审核语义。

原始需求可按功能设计，派生展示可按模块、区域或操作组织；绑定关系是明确源数据，不能在生成时凭页面按钮或关键词猜测。公共内容使用 context 集中引用。源文档中不明确的页面或操作划分，需要先作出并保存设计；不能要求程序推断。

## 手动修订与兼容

用户仍可手改 Spec。差异保留到对应 PRD/架构修订并完成候选核对之后，再重新派生。保存不等于同步，派生不等于产品确认。完整路径见派生合同，不要求每次保存启动 Agent。

尚未明确迁移的历史 Spec 继续原位编辑、工作台读取和普通/gate 保存；不能套用新派生覆盖已有正文。旧格式实质修订仍按 [既有 Spec 复核 Agent](../agents/spec-reviewer.md) 检查本批来源、语义和工程一致性；纯格式及链接检查改动即可。不得以兼容为由重新启动整份 PRD 的重写。

工作台沿现有 MODULE、页面、节点 ID、类型、contentBlocks 与 relation 协议；只有 ACTION/SURFACE 映射 DOM，其他类型供关联阅读。页面可见不证明业务权限或接口成立。JSON 仅为工作台投影，不替代 Markdown，也不用于重建并覆盖全文。需要转换时读取 [projection.md](projection.md)，需要操作工作台时读取 [mapping-workflow.md](mapping-workflow.md)。

## 3.6 验收与变更影响

HTML 交付仍按实际范围完成：

1. 核对受影响源码、模块读写边界、共享对象、复用组件及本批接口/数据影响，修改回唯一维护源。
2. 重新构建；在独立目录按约定双击或启动方式打开最终文件，检查入口、刷新与返回、代表性完整旅程及关键分支、数据恢复/重置、适用视口和资源；要求离线时断网验证。
3. 修复影响使用的脚本、资源或网络错误并复测。一次性草图按实际范围裁剪；开发服务可用、文档字段齐全或上报成功不能代替验证。

完整开发检查页面、服务端、持久化、重新查询和适用部署环境。验收依据来自 PRD 的产品结果及架构对关键机制的验证要求，关联具体来源；不在派生时新增验收业务规则。页面变更后沿 Skill 主入口核对 PRD、适用架构和 Spec；分别报告实际结果、未知、仿真与确认程度。
