# Workplace AI integration

This is the local integration contract for the upstream Diagram Design skill. It keeps the workspace's Project, evidence, asset, and validation chains intact while changing the diagram rendering method.

## 1. Scope and routing

1. Read `skills/_index.md`, then use `projects/_index.md` to select one Project; read its applicable `AGENTS.md`, stable entry and activity progress only when the diagram task needs them.
2. Facts come from the user's current instruction, the selected Project's formal entries, and direct sources. A polished diagram does not promote an assumption, historical note, candidate, or target design into a confirmed fact.
3. `product-documentation` owns product-blueprint, PRD, and Spec prose. `diagram-design` turns supported relationships into diagrams. It does not replace `frontend-implementation`, `web-prototype`, or the workspace architecture atlas.
4. Workspace-wide Project/Skill/Agent relationships still use `workspace-architecture-atlas`; a product or business diagram uses this skill.

## 2. Existing diagram sets remain valid

- Do not bulk-migrate, rename, or delete existing files under `projects/{project}/drafts-diagrams/` or historical `drafts-prototypes/business-flow/` paths.
- If a diagram set declares PlantUML or Mermaid as its maintenance source, keep that source canonical until the user explicitly approves migration. Update the declared source first, then redraw or add a Diagram Design HTML presentation derived from it.
- Preserve existing `coverage.md`, `figjam-link.md`, source filenames, version markers, and Project context links. Additions are incremental.
- A Diagram Design redraw must include a fidelity ledger in `coverage.md`: source diagrams read, nodes/relations retained, merged or omitted content, and the reason for every omission.

## 3. New diagram-set layout

New formal diagram sets use:

```text
projects/{project}/drafts-diagrams/{topic}/
  coverage.md
  html/
    01-{slug}_v0.1_YYYY-MM-DD.html
  exports/
    optional SVG or PNG requested by the user
  plantuml/
    existing or explicitly requested maintainable source
  mermaid/
    imported source or explicitly requested collaboration source
  figjam-link.md
    only when FigJam collaboration is explicitly requested
```

The self-contained HTML is the default new visual deliverable. SVG/PNG export is still on request, as required by the upstream skill. PlantUML, Mermaid, and FigJam are not generated by default for a new set, but they remain supported inputs or explicit collaboration/maintenance outputs.

## 4. Coverage before layout

For a formal business, product, clinical-safety, governance, or implementation flow, create or update `coverage.md` before drawing. It must minimally cover:

- main path;
- release/non-blocking branches;
- blocking branches;
- failures, manual repair, or compensation;
- state transitions and their triggers;
- current implementation, target addition, candidate, and pending-confirmation boundaries;
- direct source for each material rule or relation.

If the coverage cannot close, list unresolved items. Do not use visual simplification or the upstream remove test to delete a load-bearing rule. Split into overview and detail diagrams when the complexity budget is exceeded.

## 5. Optional PlantUML, Mermaid, and FigJam

- When the user explicitly asks for a maintainable UML source, use PlantUML activity, sequence, state, or class/object syntax as appropriate and keep it in `plantuml/`.
- When importing Mermaid, preserve the source in `mermaid/` and follow `import-mermaid.md`; Diagram Design HTML is the editorial redraw, not a silent replacement of source semantics.
- When the user explicitly requests FigJam, first load the required Figma diagram skills. Keep Mermaid or another local source plus `figjam-link.md`; FigJam is a collaboration layer, not the only source.
- Never make mutually exclusive branches appear sequential merely to fit a visual type. Split success, block, and repair sequences when needed.

## 6. Validation and write-back

Before delivery:

1. Reconcile every `coverage.md` item to a diagram or an explicit unresolved entry.
2. Run `python3 skills/diagram-design/scripts/self_check.py <diagram.html>` for every new or changed Diagram Design HTML.
3. Open each changed HTML in a browser when possible and check legibility, overflow, fonts/fallbacks, accessible title/description, and the primary reading path. A static check alone is not visual acceptance.
4. Verify that current, target, candidate, simulated, and pending-confirmation meanings are not mixed.
5. Update the Project context or diagram index only when its current scope or continuation entry changed. Record long-lived decisions in Project memory only when the `project-memory` rules apply.
6. If Skill routing, asset ownership, or workspace-wide relations changed, run `workspace-architecture-atlas`, `python3 scripts/audit_workspace.py`, and `python3 -m unittest scripts.tests.test_audit_workspace`.

Machine checks establish bounded validation only. User acceptance remains the only basis for `confirmed`.
