# ADR-0008：评审会话不得替代正式 PRD 状态

## 原因与边界

PRD 批注分支已经实现同一 Codex 任务中的多批意见、修订预览和合作停止，但“结束评审”只关闭会话，不能表达用户确认整份文档。正式 PRD、评审会话和反馈批次由不同职责拥有，必须分开记录。

本次将该能力迁入当前主干，并让文档状态决定是否进入评审。明确不改变 HTML 完成上报的文档同步职责，不让浏览器直接写 PRD，不把 revision、格式校验、批次发布或会话结束当成产品确认。

## 决定

- 正式 PRD 状态由产品文档流程拥有：`草稿 → 评审中 → 已确认 → 已替代`。现有带说明的中文状态按其前缀识别；未知状态仍可阅读，但不能完成确认。
- PRD 新建或发生范围、流程、角色、规则、状态、权限、验收等语义变化，且状态仍为草稿或评审中时，当前任务在文档同步和校验后调用 `open_prd_review`。仅排版、日期或无内容变化不启动。
- 评审会话独立记录 `reviewing / confirmation_requested / confirmed / ended`；其中 `confirmation_requested` 只表示用户提出确认，`confirmed` 只在正式文件复核通过后写入，`ended` 只表示停止本次协作。
- 用户只有在没有未发草稿、等待/处理中批次、待核对旧批次且当前 revision 一致时，才能请求“确认当前版本”。请求返回原 Codex 任务，由 `$product-documentation` 更新并冻结正式文件；工作台只在重新读取到 `已确认` 状态、相同产品与稳定需求 ID、除文档状态外正文未变，并匹配最终 revision 后显示确认完成。
- 批次状态继续由队列服务拥有，停止不回滚已经写入的正文；确认请求期间不得再提交批注或发布修订。

## 否决方案

- 把 `publish_html_ready` 当作 PRD 审核入口：它发生在文档同步之前，也覆盖不需要改 PRD 的 HTML，且无法服务仅 PRD 修订。
- 把“结束评审”改名为“确认”：没有正式文件状态与冻结证据，会制造虚假确认。
- 由工作台直接修改或移动 PRD：会形成绕过产品文档 Skill 的第二条正文写入链。

## 回归检查

- 插件工具清单同时包含 HTML 上报与 PRD 批注/确认工具，已安装版本单独验证。
- 草稿或评审中 PRD 可进入批注；已确认或已替代版本不能作为可写评审源。
- 有未处理草稿或批次时拒绝确认；会话结束仍保持未确认。
- 确认请求只在原任务完成正式文件写入、路径与 revision 校验后变为已确认。
- `npm run verify` 覆盖服务、MCP、浏览器流程和现有 HTML 文档同步回归。
