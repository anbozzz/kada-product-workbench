# 可移植只读评审包

## 原因

评审后的功能页面、PRD、Spec 与已确认映射需要交给研发持续查看，但当前产品只有本机工作台。直接暴露现有 HTTP 服务会同时暴露项目扫描、文件选择、Spec/Map 写入和 Codex 编排；把大型页面强行内嵌为单 HTML 又会造成体积、模块加载和资源路径问题。

## 决定

- 在现有工作台顶部增加“导出”入口，不新增页面、模式或平行项目中心。
- 默认产物是 ZIP 只读评审包。包内冻结当前功能页面包、工作台静态资源、PRD、Spec、两类 Map、来源 revision 与 manifest。
- ZIP 只打包已选 HTML 入口同目录下的运行时资源，不打包项目根、`.git`、`node_modules`、源码、缓存或 source map；符号链接不跟随。
- 本地开发地址不推断构建产物。没有已选 HTML 页面包时失败关闭，并提示先构建或选择 HTML 入口。
- Windows x64 评审者默认双击包内 `打开评审.exe`，不要求预装 Node；macOS 和技术兜底继续使用 `open-review.mjs`、`.command` 与 `.bat`。各启动器只读取同一份冻结文件，不建立第二套评审逻辑。
- 评审包查看器仅监听 `127.0.0.1` 的随机端口。它只提供冻结配置、工作台静态资源与页面资源；所有 `/api/*` 写入、项目管理、文件浏览和 Codex 能力均不可用。
- 导出前先保存当前等待中的 Spec Map；保存失败则不生成包。PRD 页面关系继续沿用现有显式保存规则。
- 导出配置清除工具持有的本机绝对路径和项目目录，只保留产品名、版本、revision、生成时间、入口相对路径和文件校验摘要；PRD/Spec 正文内由作者明确写入的来源内容不在此处擅自改写。

## 明确不改

- 不改变 Markdown Spec、内部 JSON 投影、HTML、`prd-map.json` 或 `spec-map.json` 的所有权和写回方向。
- 不把导出视为产品确认、实现验收或评审通过。
- 不为动态后端、登录态、WebSocket 或外部接口伪造离线能力。
- 不增加公网发布、账号、权限或多人评论。
- 不在当前阶段伪造企业代码签名；正式跨组织分发前应由发布方使用可信证书签署 Windows EXE，未签名包可能显示“未知发布者”。

## 否决方案

- 直接把当前工作台监听到局域网或公网：只读查看与本机写能力没有安全隔离。
- 默认单 HTML：大型项目资源膨胀，ES Module、根路径资源和页面路由在 `file://` 下不可靠。
- 压缩整个项目目录：会泄露源码、版本历史、依赖缓存和无关资料。
- 为导出另建独立工作台：会复制评审交互并造成长期漂移。
- 每个 ZIP 内附带完整 Node for Windows：实现简单但会让所有评审包额外膨胀数十 MB，并暴露远超只读查看所需的通用运行时。

## 回归检查

- 原入口仍可切换绑定/评审模式、打开相关 PRD、查找 Spec、查看绑定状态、离开和保存。
- 导出入口在同一顶部操作区可达，窄屏时不挤占产品标题和工作模式。
- Windows x64 解压后无需安装依赖即可用 EXE 启动；Node 20 兜底入口仍可用。两种入口都只监听本机，页面滚动、点击、缩放、Spec 标记/查找和 PRD 阅读可用。
- Windows EXE 具有有效 PE 头，只包含只读 HTTP 查看职责；所有 `/api/*` 写接口返回只读错误。
- 评审包的配置没有本机绝对路径，所有写入和项目管理 API 返回只读错误。
- 本地开发地址、越界资源、符号链接和不允许的源码类型不会进入 ZIP。
